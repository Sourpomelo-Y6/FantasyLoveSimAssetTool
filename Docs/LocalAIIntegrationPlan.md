# LocalAIEventPrototype 統合計画

## 1. 目的

`LocalAIEventPrototype` で検証したローカルAI連携を `FantasyLoveSimAssetTool` に取り込み、ヒロインごとの会話、イベント、戦闘、訓練、衣装反応などの文章制作を支援する。

AssetToolをゲームデータの正本として維持し、AIは既存データを直接管理する主体ではなく、編集可能な文章案を生成する補助機能として扱う。

UIデザインは、現在のAssetToolよりも生成工程、状態、再実行箇所が分かりやすい `LocalAIEventPrototype` を基準とする。ただし、Prototypeの画面をそのまま追加するのではなく、AssetToolの既存タブとデータ構造へ統合する。

## 2. 確認した現状

### LocalAIEventPrototype

Prototypeには次の機能がある。

- llama.cppのOpenAI互換APIへの接続
- `/v1/models` によるモデル一覧取得と接続確認
- JSON Schemaを指定した構造化テキスト生成
- コードフェンスや余分な文章を含む応答の解析
- Character / Emotion / Action / Stateからのプロンプト合成
- ComfyUI画像生成
- Visionモデルによる画像説明
- バッチ生成、キャンセル、失敗項目の再試行
- 生成時プロンプトと生レスポンスの確認

再利用の中心は `Services/LlamaCppClient.cs` の通信処理と構造化応答処理である。画面、イベント専用モデル、`Characters.json` はAssetToolの構造と重複するため、そのまま移植しない。

### FantasyLoveSimAssetTool

AssetToolの `HeroineProfile` には、AI生成に必要な次の情報がすでにある。

- 名前、性格、話し方
- 一人称、二人称
- 好きなもの、嫌いなもの
- 朝、夜、ゲーム開始時などの固定台詞
- 行動反応方針、エンディング方針
- 衣装別メッセージ
- 通常会話、ゲームイベント、行動反応、予定イベント、エンディング
- 戦闘結果、戦闘パネル、単独帰還時のメッセージ
- 訓練中の台詞

したがって、キャラクター設定の正本はPrototypeの `Characters.json` ではなく、AssetToolのヒロイン別 `profile.json` とする。

## 3. 基本設計

文章生成は次の4層からプロンプトを構築する。

```text
共通の執筆指示
  + ヒロイン設定
  + 文言種類別テンプレート
  + 現在の場面・ゲーム条件
```

### 共通の執筆指示

- 恋愛シミュレーションゲーム向けの自然な日本語にする
- 設定にない事実を勝手に確定しない
- 一人称、二人称、口調を守る
- 指定された長さと出力形式を守る
- 制作メモやプロンプトをゲーム本文へ混ぜない
- 指定されたJSONだけを返す

ワークスペース共通設定として保存し、ヒロインデータとは分離する。

### ヒロイン設定

`HeroineProfile` から名前、性格、話し方、一人称、二人称、好み、各種方針を自動的に収集する。

口調の安定化のため、将来次の項目を追加する。

- `SpeechExamples`: 代表的な台詞3～5件
- `ForbiddenExpressions`: 禁止する語尾や表現
- `BackstorySummary`: AIが参照してよい背景情報
- `PlayerRelationshipPolicy`: 好感度帯ごとの距離感
- `WritingNotes`: 全文言へ適用する演技上の注意

既存の朝、夜、開始時台詞は口調例として利用できるが、固定文言と参考例を区別してプロンプトへ渡す。

### 文言種類別テンプレート

共通指示とキャラクター設定だけでは、短いUI文言と複数ページのイベント本文を安定して書き分けられない。そのため、用途ごとに次を定義する。

- 生成目的
- 文字数または行数
- 必須の意味
- 禁止事項
- 出力JSON Schema
- 利用できる表情、話者などの候補
- 既存文との重複を避けるか

対象テンプレートの例：

- `morning_greeting`
- `outfit_changed_message`
- `training_dialogue`
- `battle_panel_message`
- `conversation`
- `game_event`
- `action_reaction`
- `scheduled_event`
- `ending`

### 現在の場面・ゲーム条件

生成時に選択中のデータから、必要な情報だけを渡す。

- 会話種別、カテゴリ
- 好感度範囲
- 場所、行動、時間、季節、天候
- 衣装、戦闘結果、訓練状態
- イベントタイトル、制作メモ
- 前後の台詞
- 使用可能な表情ID

ID、発火条件、priority、参照Asset IDなど、ゲーム構造に関わる値はAIに自由決定させない。画面で指定した値を維持し、AIは主にタイトルと本文を生成する。

## 4. サービス構成

```text
AssetToolの各編集画面
        ↓
LocalTextGenerationService
        ↓
PromptComposer
  ├ 共通指示
  ├ HeroineProfile
  ├ タスク別テンプレート
  └ 選択中の条件
        ↓
ILocalLlmClient / LlamaCppClient
        ↓
構造化結果と検証結果をプレビュー
        ↓
利用者が採用
        ↓
既存の保存・Export処理
```

通信クライアントはGemmaやQwenなどの固有名に依存させず、OpenAI互換APIを提供する任意のローカルモデルを選択できる設計にする。

AI応答を受け取った時点では既存データを変更しない。生成結果のプレビューから「採用」を実行したときだけ編集モデルへ反映し、保存は既存の保存コマンドで行う。

## 5. UI方針

### Prototypeから採用する要素

- 暗色ベースのパネルとアクセントカラー
- 大きなセクション見出しと工程番号
- 左右2カラムによる入力条件と結果の分離
- 接続中、生成中、成功、失敗のステータスバッジ
- 主要操作を大きく見せるボタン
- 詳細な接続設定や生レスポンスを `Expander` へ収納
- 入力、生成結果、生レスポンスを画面内で確認できる構成
- 失敗しても完了済みの結果を保持し、該当工程だけ再実行できる操作
- 画面下部の常時表示ステータス

### AssetTool向けの適用方法

Prototypeの単一イベント生成画面を丸ごと追加せず、AssetToolの各タブに共通の「AI文章支援パネル」を設ける。

```text
選択中データと生成条件
        │
        ├ AI生成
        ├ 別案を生成
        └ 空欄のみ一括生成

生成候補
        ├ 候補1
        ├ 候補2
        └ 候補3

[採用] [再生成] [破棄]
```

通常利用では接続設定や生レスポンスを隠し、必要なときだけ展開する。大量の既存項目を扱うAssetToolでは、Prototypeの視認性を保ちながら画面の縦方向への肥大化を避ける。

共通スタイルは `ResourceDictionary` に分離し、既存タブへ段階的に適用する。最初から全画面を一括変更せず、LocalAI設定画面とAI文章支援パネルでデザインを確立してから既存画面の整理へ広げる。

## 6. AI生成対象の導入順

### 第1段階: 短い固定文言

- 朝と夜の挨拶
- 初期台詞、次の行動を促す文言
- 衣装ロック、衣装変更、衣装反応
- 戦闘パネル結果メッセージ
- 単独帰還反応
- 訓練中の短い台詞

1件生成、別案3件、空欄のみ一括生成を提供する。

### 第2段階: 会話とイベント本文

`ConversationEntry` と `ConversationLine` に対応した構造化JSONを生成する。

```json
{
  "title": "...",
  "lines": [
    {
      "speaker": "Heroine",
      "text": "...",
      "expression": "Smile"
    }
  ]
}
```

対象は通常会話、GameEvents、ActionReactions、ScheduledEvents、BattleResultEvents、Endingsとする。既存行の置換、続き生成、別案生成を区別する。

### 第3段階: バッチ生成と品質検査

- 好感度帯ごとの通常会話
- 各ジャンルのフォールバック会話
- 訓練状態ごとの候補
- 戦闘結果、衣装、季節、天候の差分
- 空欄のみ、選択項目のみ、失敗項目のみの実行
- キャンセルと個別再試行

生成後に一人称、二人称、禁止表現、長さ、重複、話者、表情IDを検査する。

### 第4段階: 画像・Vision連携

- AssetToolの登録画像またはComfyUI生成画像を入力
- VisionモデルでScene Descriptionを生成
- Scene Descriptionとイベント条件から本文を生成
- 画像、文章、使用プロンプトの対応を記録

まずテキスト生成を安定させ、その後に追加する。

## 7. 実装フェーズ

### Phase 1: LLM基盤

- `ILocalLlmClient` と `LlamaCppClient` を追加
- URL検証、モデル一覧、接続テスト
- タイムアウト、キャンセル、空応答、HTTPエラー処理
- JSON Schemaと応答解析
- AssetToolは現在.NET 5のため、Prototypeのコードを.NET 5互換へ調整する

### Phase 2: 設定とプロンプト合成

- `LocalAISettings` を追加
- 共通指示とタスク別テンプレートを外部ファイル化
- `HeroineProfile` からキャラクターコンテキストを生成
- 送信プロンプトのプレビュー
- 接続設定とゲームデータを分離

保存構成案：

```text
LocalAISettings/
├ connection.json
├ base-instruction.txt
└ text-tasks.json
```

秘密情報を扱うようになった場合はGit管理対象へ平文保存しない。

### Phase 3: 短文生成UI

- Prototype準拠の共通スタイルを作成
- LocalAI接続・モデル設定画面を追加
- 選択フィールド用のAI文章支援パネルを追加
- 候補生成、採用、再生成、破棄、元に戻すを実装
- 戦闘と訓練の空欄一括生成を追加

### Phase 4: 会話・イベント生成

- `ConversationEntry` を生成入力へ変換
- 複数行の構造化出力を解析
- 登録済みの話者、表情だけを許可
- 生成結果へ既存の検証処理を実行

### Phase 5: バッチと品質管理

- 進捗、キャンセル、個別失敗、再試行

- 生応答とエラーを確認できるログ

### Phase 6: 画像・Vision統合

- PrototypeのVision処理を汎用化
- AssetToolのComfyUI生成・登録画像と接続
- Scene Descriptionを編集可能な中間結果として保持

## 8. 最初のMVP完了条件

1. AssetToolからllama.cppへ接続確認できる
2. 共通指示を編集・保存できる
3. 選択中の `HeroineProfile` からキャラクター設定を構築できる
4. 短い文言を候補として3件生成できる
5. 採用前は既存データを変更しない
6. 採用後も既存の保存操作を行うまでファイルを書き換えない
7. 戦闘・訓練の空欄のみ一括生成できる
8. 通信失敗、解析失敗、キャンセルで既存データを失わない
9. 接続、解析、プロンプト合成、採用処理のテストがある
10. LocalAI設定画面と支援パネルがPrototype準拠の視覚設計になっている

## 9. 設計上の決定

- キャラクター設定の正本はAssetToolの `HeroineProfile` とする
- Prototypeの独立したイベントモデルと `Characters.json` は統合後の正本にしない
- AIは文章案を生成し、ID、条件、priority、Asset参照はAssetToolが管理する
- AI応答を直接保存せず、必ずプレビューと採用操作を通す
- 共通指示だけでなく、文言種類別テンプレートと現在条件を使用する
- UIはLocalAIEventPrototypeをデザイン基準とする
- 3段目のタブは、情報のまとまりを分けて画面を整理できる場合には使用してよい。ただし、AI入力補助と、そのAIが編集・補完する入力対象は同じページに配置し、現在値、生成候補、採用結果をタブ移動なしで確認できるようにする
- UI全体の刷新とLocalAI機能追加を同時に行わず、共通スタイルとAI支援画面から段階的に適用する
- テキスト生成を先に完成させ、Visionと画像連携は後続フェーズにする

## 10. 実装状況（2026-08-25）

当初計画のうち、短文生成を中心とするMVPと衣装メッセージ連携は実装済みである。会話・イベント本文の生成、全項目の一括生成、Vision連携は未着手または後続候補として残っている。

### 実装済み

- llama-server互換APIへの接続設定、モデル取得、接続テスト
- タイムアウト、キャンセル、空応答、JSON解析失敗、HTTPエラーの表示
- エラー詳細と生レスポンスを選択・コピーできる読み取り専用テキスト欄
- 共通の基本指示と、選択中ヒロインのキャラクター設定を使ったプロンプト合成
- ローカルLLMへ渡す情報を生成対象に必要な項目へ絞るコンテキスト生成
- 3候補の生成、未生成候補の再生成、候補の採用、文字数検証
- 選択中の会話台詞1行に対するAI候補生成。直前2行と主要条件だけを文脈に含め、会話項目または台詞行の切り替え時には候補を破棄する
- 会話台詞候補ごとに登録済み表情IDから1件を提案し、本文と一緒に採用するか、本文だけ採用するかを選択できる
- 選択中の会話項目に対する最大3行の下書き生成。別表で確認し、既存行への追加または置き換えを選択できる。ID、条件、好感度、画像、選択肢は変更しない
- 状況テンプレートから新規の通常会話項目を準備し、カテゴリ、仮タイトル、重複しないIDを設定する導線。条件は人が設定し、保存まではファイルへ書き込まない
- 複数行の会話下書きに対する品質検査。既存台詞との重複・類似、下書き内類似、長さ、話者・表情ID、制作指示・内部ID・禁止表現の混入、状況カテゴリ不一致を行単位で警告する。警告があっても自動修正や自動保存はしない
- 会話台詞AI候補の生成元を追跡し、別項目・別行への誤採用を防ぐセッション検証と、採用前後の非破壊動作テスト
- 採用するまでは編集データを変更せず、採用後も通常の保存操作まではファイルを書き換えない動作
- 共通短文用と衣装メッセージ用で再利用する `LocalAiShortTextPanel`
- パネルの配置場所に応じた生成対象の絞り込み
- 基本情報を「プロフィール」と「ゲーム設定・台詞」に分割したUI
- 衣装メッセージを独立ページにし、衣装用AI操作も同ページへ配置
- 衣装定義から不足している衣装メッセージ行を作成し、対象の表へ移動する操作
- 衣装反応の固定4種（`Praise`、`Dislike`、`Bored`、`Change`）の不足行を補完する操作
- 衣装メッセージと衣装反応に表情IDを設定・検証・保存する機能
- AIが衣装文言を生成する際、登録済み表情IDから候補表情も提案する機能
- AssetToolからUnityへの衣装文言・表情IDの書き出しと読み戻し
- 戦闘スキル名、訓練スキル名・説明文、スキルツリーノード名のAI候補生成
- スキル文章候補の重複、内部設定値、明らかな効果矛盾、候補間類似の警告

### 現在の生成対象

通常位置では、ゲーム開始、朝、夜などの短い固定文言を選択できる。衣装メッセージ位置では、着用中、着替え後、衣装反応に対象を限定する。これにより、同じAIパネルを複数の位置から使いつつ、誤った項目を選びにくくしている。

衣装用候補では文言と表情IDを一組として表示する。表情を採用するかどうかはチェックボックスで選べるため、文言だけを採用して既存の表情を維持することもできる。AIへ渡す表情IDは最大20件に制限し、応答値が登録済み一覧に完全一致する場合だけ採用候補とする。

### 衣装メッセージのデータ連携

| 用途 | AssetTool | 書き出しJSON | Unity |
| --- | --- | --- | --- |
| 衣装識別子 | `OutfitId` | `outfitId` | `OutfitMessageOverride.outfitId` |
| 着用中の文言 | `LockedMessage` | `lockedMessage` | `lockedMessage` |
| 着用中の表情 | `LockedExpressionId` | `lockedExpressionId` | `lockedExpressionId` |
| 着替え後の文言 | `ChangedMessage` | `changedMessage` | `changedMessage` |
| 着替え後の表情 | `ChangedExpressionId` | `changedExpressionId` | `changedExpressionId` |
| 反応種別 | `ReactionType` | `reactionType` | 衣装反応種別 |
| 反応文言 | `Message` | `message` | 反応メッセージ |
| 反応表情 | `ExpressionId` | `expressionId` | 反応時の表情ID |

書き出し前の検証では、表情IDが未入力または定義一覧に存在しない衣装メッセージを検出し、該当する衣装行へ移動できる。Unity側では衣装別設定を読み込み、着用中・着替え後・反応時の表情へ反映する。

### 推奨する編集手順

1. ヒロインを選択し、Local AI設定で接続先、モデル、基本指示を確認する。
2. 衣装定義から不足している衣装メッセージ行を作成する。
3. 固定4種の衣装反応行を補完する。
4. 対象行を選び、AIから文言候補を生成する。
5. 文言と、必要なら提案された表情を採用する。
6. AssetToolの検証を実行し、未入力・不明な表情参照を修正する。
7. 通常の保存操作を行い、Unity向けデータを書き出す。
8. Unity側でインポートし、実際の表示と表情切り替えを確認する。

### スキル文章AI支援の扱い（保留）

戦闘スキル名、訓練スキル名・説明文、スキルツリーノード名の候補生成機能は実装済みだが、2026-08-25時点では生成されるスキル名の品質が期待水準に達していない。このため、スキル名関連のAI機能は試験的機能として残し、当面は手動編集を基本とする。

次の作業は後回しとし、通常の優先候補には含めない。

- スキル名生成の追加調整、生成対象の拡大
- 説明文が空の訓練スキルを順番に補完する処理
- スキル文章の一括生成、自動採用
- スキルの効果、対象、数値まで含む構造化生成

再開する場合は、先に採用したいスキル名と採用したくないスキル名のサンプルを用意し、命名規則、世界観、語彙、長さを明文化する。その評価セットに対してモデルとプロンプトを比較し、品質を確認してから機能追加を行う。現在の品質警告は補助的な検出であり、スキル名の良し悪しを保証するものではない。

### 会話データUIとAI入力補助の計画

会話データタブは、一覧、本文、条件、演出、画像、音声、選択肢などが同じ画面に集まり、選択中の会話行を編集する際の視線移動とスクロール量が大きくなっていた。このため、機能を削らず用途ごとに配置を整理した。

2026-08-25に会話項目の一覧を常時表示したまま、右側の編集領域を次の2ページに分割した。各ページは縦スクロール可能とし、台詞行と選択肢の一覧には最低表示高さを設定した。「条件・演出」ページは「発生条件」「画像・演出」「メモ」の折りたたみ欄に整理し、利用頻度の高い発生条件だけを初期展開する。

1. 本文編集
   - 会話データ種別と会話項目の選択
   - 台詞行の一覧と選択中行の編集
   - 話者、本文、表情、音声
   - 選択中の台詞本文に対するAI候補
2. 発生条件・演出
   - カテゴリー、優先度、Once設定
   - 日時、場所、天候、季節、衣装などの発生条件
   - 好感度変化、画像、演出、選択肢
   - 使用頻度が低い詳細設定

3段目のタブ分け自体は禁止しない。情報量が多い設定を意味のまとまりごとに整理できる場合は使用する。ただし、「入力対象」と「その項目を生成・補完するAI入力補助」を別タブに分けない。AI入力補助は対象となる本文や選択中の台詞行と同じページ内に、折りたたみ欄などで配置し、現在値と生成候補を見比べながら採用結果を確認できるようにする。今後、条件、画像・演出、選択肢などをAIの入力対象に追加する場合も、各対象と対応するAI操作を同じページに置く。

詳細条件、画像・演出、選択肢などは、必要に応じて3段目のタブまたは `Expander` で意味のまとまりごとに分ける。ただし、会話項目と台詞行の選択、選択中本文は常に見える状態を維持する。折りたたみを展開した際に主要な一覧が消えないよう、ページ全体を縦スクロール可能にし、一覧には最低表示高さを確保する。

最初のAI入力補助として、選択中の台詞本文だけを対象に実装した。ローカルLLMへ渡す情報は次に限定する。

- ヒロインの名前、性格、口調、一人称、二人称
- 会話データ種別と選択中項目のID・カテゴリー
- 選択中行の話者
- 文脈として必要な直前の台詞（最大2行程度）
- 場所、時間帯、衣装など、設定されている主要条件
- 文字数と出力形式

候補は3件生成し、採用するまで既存本文を変更しない。採用後も通常の保存操作まではファイルを書き換えない。生成中に会話項目または行を切り替えた場合は、生成元が変わった候補を破棄して誤採用を防ぐ。既存の文字数、重複、内部設定値混入などの品質警告を可能な範囲で再利用する。

次の機能は初回実装に含めず、選択中1行の生成が安定してから検討する。

- 会話全体や複数行の一括生成
- 選択肢と分岐の自動生成
- 発生条件や好感度変化のAI決定
- 既存本文の自動上書き、自動採用
- 全会話の空欄一括補完

実装順は、現行UIの項目対応を確認して2ページへ再配置し、既存の保存・検証・移動処理が変わらないことをテストした後、選択中1行のAI候補生成を追加する。UI整理とAI処理を同時に大きく変更せず、各段階で動作確認できる状態を維持する。

### Heroine3（クーデリア）を基準にした会話用追加プロンプト計画

既存データ上の識別子は `Heroine3`、表示名はクーデリアである。Unity側の `Assets/Resources/Heroines/Heroine3Profile.asset` と `Assets/Resources/Heroines/Heroine3/Conversations/` 以下の既存会話を参考資料として、会話データ生成用の追加プロンプトを作成する。ただし、既存台詞をそのまま大量にプロンプトへ入れるのではなく、傾向を短く整理した指示と少数の例へ縮約する。

2026-08-26に初版として、日常、冒険、食事、恋愛の状況テンプレート4件と、クーデリア固有プロンプトを作成した。その後、Heroine3の既存会話に見られる朝の誘い、相手の一日を聞く会話、悪天候の室内時間、未知の場所、危険時の休息、冒険中の信頼、食の好み、相手のための食事、季節の一品、関心の芽生え、静かな親密さ、高好感度の告白をキャラクター非依存の12テンプレートへ抽象化し、合計16件へ拡張した。既存台詞そのものやクーデリア固有の口調は共通テンプレートへ含めない。JSONの読み込み、状況指示を先にした合成順序、参考台詞を最大3件に制限する処理を実装し、選択中の会話行を生成するAI入力補助へ接続した。状況テンプレート選択、固有プロンプトの読み込み状態、今回だけの追加指示、合成結果のプレビューを同じ本文編集ページで確認できる。テンプレートを選択しない場合は従来の1行生成を維持する。さらに、選択中の会話項目へ1～3行の下書きを1案生成し、プレビュー後に追加または置き換えを選ぶ機能と、選択した状況から新規会話項目を準備してそのまま下書き生成へ進む導線を実装した。

追加プロンプトは次の2層に分け、生成時に合成する。

1. 状況プロンプト（キャラクター非依存）
   - 日常、冒険、食事、恋愛、訓練などの会話目的
   - 場所、時間帯、季節、天候、衣装、好感度段階
   - 会話の開始点、話題、感情の流れ、終了状態
   - 必要な話者と行数、選択肢の有無、文字数、出力形式
   - キャラクター名、固有の口調、固有設定は含めない
2. キャラクター固有プロンプト
   - 名前、一人称、二人称、性格、口調、プレイヤーとの距離感
   - 感情ごとの表現傾向、好意の示し方、避ける表現
   - `Heroine3` の既存台詞から抽出したクーデリアらしい語尾、言い回し、会話テンポ
   - 参考例は短いものを最大3件程度に制限し、既存台詞の単純な再出力を禁止する

ローカルLLMへ渡す順序は、`基本指示 → 状況プロンプト → キャラクター固有プロンプト → 選択中会話の構造情報 → 出力形式` とする。状況プロンプトを別キャラクターでも再利用でき、キャラクター固有プロンプトの差し替えだけで同じ状況の会話を作れる構成にする。現在と同様、直前の台詞は最大2行、登録済み表情IDは最大20件とし、コンテキストを増やしすぎない。

保存先は、状況プロンプトを `PromptTemplates/conversation-situations.json`、キャラクター固有プロンプトを `Characters/<HeroineId>/conversation-ai-prompt.json` とした。前者は全キャラクター共通のテンプレート、後者はキャラクターデータと一緒に管理・バックアップできる設定とする。正式な編集UIを実装する際には既存のワークスペース移行、保存、バックアップ処理への追加要否を確認する。

バンドル版へ状況テンプレートが追加された場合、起動時に作業フォルダーの同JSONへ未登録の `situationId` だけを追記する。既存IDの内容はユーザー編集を優先して上書きしない。ただし、旧形式で `suggestedConditions` 自体がない場合だけ、同じIDのバンドル推奨条件を補完する。ユーザーが推奨条件を設定済みなら維持する。作業フォルダー側のJSONが不正な場合も自動上書きせず、そのまま保持する。

状況テンプレート選択欄は件数増加に対応し、`すべて / 日常 / 冒険 / 食事 / 恋愛` の種類フィルターを持つ。種類を変更したときは該当テンプレートだけを表示し、その種類の先頭候補を選択する。

会話データ画面上部の操作は、選択中データ種別と「現在の種類をUnityから読み込む」操作へ整理する。5種類の個別読込ボタンは `Unity読込の詳細` に折り畳んで残す。会話項目の新規追加・削除は対象が明確になるよう左側一覧の見出しへ移し、標準メニュー準備は会話画面から除いて `メニュー設定` タブへ集約する。

実装は次の順序で進める。

1. `Heroine3` のプロフィールと既存会話を、ジャンル、好感度、時間、天候などで分類する。
2. クーデリア固有の話し方と関係性の変化を要約し、キャラクター固有プロンプトの初版を作る。
3. キャラクター情報を含まない状況テンプレートを数種類作り、クーデリア固有プロンプトと組み合わせて比較する。
4. AssetToolに状況テンプレート選択、追加指示、合成プロンプト確認のUIを追加する。
5. 最初は選択中の会話項目または台詞行だけをプレビュー生成し、人が採用する。会話の一括生成と自動保存は行わない。

初回評価では、日常、冒険、食事、恋愛から各1状況を選び、既存データとの重複、クーデリアらしさ、状況への適合、行数と文字数、表情IDの妥当性を確認する。この評価後に、状況テンプレートの追加や複数行会話の生成へ進む。
